# CairnPath Envelope / CHRONOS Carrier Reconciliation

Status: v0.1 analysis note. Not a schema change, not an authority decision. Written to answer one question raised alongside the KAIROS/CHRONOS thread (see `docs/integration/neurosymbolic-chronos-alignment.md`): does `cairnpath_mesh_export_pack_v0_5`'s signed event envelope duplicate CHRONOS's carrier model under different vocabulary, or is it a genuinely different primitive?

## What was compared

- CHRONOS carrier model: `docs/integration/chronos-evidence-loop.md` — `Carrier = payload + provenance + schema + validation + boundary semantics`, answering: what is carried / where from / what validates it / what authority does it have / what authority does it explicitly not have.
- `cairnpath_mesh_export_pack_v0_5`'s `schemas/envelope/frame.v0.jsonschema.json` — titled internally "TriRPC Frame Envelope v0" (the bundle's own README calls it the "TriTRPC frame envelope schema"; this doc uses "cairnpath envelope" per the task framing and notes the naming ambiguity is the bundle's own, not introduced here). Found already unzipped in this session's scratchpad at `cairnpath_mesh_export_pack_v0_5/cairnpath_mesh_bundle_v0_4/schemas/envelope/frame.v0.jsonschema.json`.

Note: per `reference_tritrpc.md` estate guidance, "TriTRPC" in this family of specs denotes a codec, not an RPC transport, and is unrelated to "TriuneRPC." That distinction doesn't change the analysis below, but is flagged so the naming isn't misread elsewhere.

## Field-by-field comparison

| CHRONOS carrier concept | cairnpath envelope field(s) | Match? |
|---|---|---|
| What is carried (payload) | `payload` (typed: object/array/string/number/boolean/null) | Direct match, but untyped at the envelope level — the envelope only carries an opaque payload plus a schema pointer. |
| What validates it (schema) | `payload_schema` (string, min length 1) | Partial match. CHRONOS's "carrier schema" is a first-class governed artifact (versioned, with a home in `schemas/`, checked by a validator, backed by fixtures — see the Carrier Surface definition). The envelope's `payload_schema` is just a string reference; the envelope schema itself does not require that string to resolve to anything, be versioned, or be validated against. |
| Where it came from (provenance) | `actor` (kind/id/kid/display_name), `context` (neighborhood/project/workspace/branch/topic/trace_id, optional), `links[]` (rel/ref/hash/media_type), `ts`, `id` (ULID) | Partial match, different shape. CHRONOS provenance is "which evidence/source did this claim come from" (an `evidenceRefs`-style chain back to a corpus or observation). The envelope's provenance is "who sent this, when, in what session/branch, linked to what" — transport/session provenance, not evidentiary lineage. `links[]` can carry a hash-pinned reference to something else, which is the closest overlap. |
| What authority it has / doesn't have (boundary semantics) | `policy` (`policy_id`/`policy_hash`/`purpose`/`decision_id`), `frame_type` (incl. `Commit`, `Governance`, `Identity`, `Policy`, etc.) | Partial match, and this is the sharpest gap. CHRONOS requires an explicit **non-authority declaration** — a carrier states, in words, what it does *not* authorize (see the `nonAuthorityDeclaration` field enforced by `tools/check_neurosymbolic_chronos.py`, and the doctrine's "Required negative rules" list). The envelope schema has no equivalent field. `policy_ref` binds a frame to a policy decision that presumably already happened elsewhere, and `frame_type: Commit`/`Governance`/`Identity` *names* a category of high-authority action, but nothing in the schema itself constrains what a `Commit` frame is allowed to commit, or requires it to declare what it is not authorized to do. |
| Validation authority (who/what checked this is admissible) | `signatures[]` (`alg`: ed25519/secp256k1/rsa-pss-sha256, `kid`, `sig`, `created_at`; `minItems: 1`) | Different axis, not really a match. Envelope "validation" is cryptographic authenticity — proof that a specific keyholder produced/attested this exact byte sequence. CHRONOS "validation" is epistemic/governance admissibility — `claimStatus`, `validationState`, grounding checks, replay lifecycle (`evidence_anchor -> ... -> governance_decision -> receipt_or_rejection`). CHRONOS fixtures today have **no signature/attestation field at all** — admissibility is asserted by structure and by an owning-plane's review, not cryptographically proven. |
| Carrier levels: schema / instance / surface | No equivalent. The envelope bundle ships one schema, some fixtures, and a validator for the envelope itself, but a given `payload_schema` string has no required matching fixture/validator/doc bundle the way a CHRONOS carrier surface does. | No match. |
| Replay / lifecycle (`expectedLifecycle`: evidence_anchor → normalized_claim → candidate_carrier → explanation_trace → verification_result → governance_decision → receipt_or_rejection → learning_update) | `idempotency_key`, `replay_nonce` (both optional) | Different axis. The envelope's "replay" concern is wire-level exactly-once/idempotent delivery. CHRONOS's "replay" concern is an epistemic state machine — has this claim moved through evidence, verification, and governance. Same word, unrelated meaning. |
| Owning authority plane | `actor.kind` (human / agent / node / service) | No match. CHRONOS carriers are plane-owned (a specific governing repo like `SocioProphet/policy-fabric` or `SocioProphet/ontogenesis` owns admission). The envelope's `actor` is a signer identity, not a governance plane — it answers "who sent this," not "which authority governs whether this is real."

## Recommendation

**Not the same primitive under two names — genuinely different layers that are compatible, not competing.**

The two specs sit on different axes of the same larger problem ("move a governed thing between parties safely"), and forcing them into one vocabulary would lose real information on both sides:

- The cairnpath envelope is a **wire/transport frame**: cryptographic authenticity (`signatures[]`), addressing and session context (`actor`, `context`, `links[]`), delivery semantics (`idempotency_key`, `replay_nonce`), and a coarse policy/action-category tag (`policy_ref`, `frame_type`). It answers "who sent this, is it tamper-evident, and don't process it twice" — questions CHRONOS's carrier model does not currently address at all (no signature field, no idempotency concept in the doctrine).
- The CHRONOS carrier is an **epistemic/governance object**: claim status, validation state, grounding, explicit non-authority declaration, and a review/replay lifecycle that ends in a governance decision. It answers "is this admissible, by whose authority, and what does it explicitly not authorize" — questions the cairnpath envelope schema does not address (no claim-status vocabulary, no non-authority declaration, no owning-plane concept).

**Recommended framing, not a decision:** treat the cairnpath envelope as a plausible *wire carrier* for CHRONOS carrier payloads when a CHRONOS carrier needs signed, addressed, multi-party transport — e.g. a `ChronosCarrierRegistration` object goes in `payload`, `payload_schema` points at the relevant CHRONOS carrier schema, and `signatures[]` supplies an attestation CHRONOS has no native answer for today. Under that framing, `frame_type: Governance` or `Commit` would be the envelope category used to move a CHRONOS governance decision or receipt across a signed channel, not a competing authority statement.

**Two real gaps, one on each side, worth flagging to the respective owners rather than resolving here:**

1. CHRONOS side: the doctrine has no cryptographic-attestation concept. If carriers ever cross a trust boundary where "who actually asserted this" needs to be provable (not just structurally declared), CHRONOS will need something like the envelope's `signatures[]` — this is a gap, not a rejection of the envelope's approach.
2. cairnpath side: `frame_type: Commit` / `Governance` / `Identity` frames carry real authority by name, but the schema has no field requiring them to state what they are *not* authorizing. CHRONOS's `nonAuthorityDeclaration` discipline (enforced today by `tools/check_neurosymbolic_chronos.py`) is directly transferable there and would close that gap without touching the wire format.

This is not a forced reconciliation. If a future reviewer concludes the two really are meant to converge into one vocabulary, that is an owning-plane decision (whichever plane ends up owning cross-repo signed transport) and should happen with its own review, not as a byproduct of this note.
